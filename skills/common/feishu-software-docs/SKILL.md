# feishu-software-docs

## 定位

这是“程序文档内容整理 + 飞书友好输出层” Skill，不是通用 Markdown Formatter。

当用户要求把程序、项目 README、模块、功能、接口、部署步骤或已有程序说明整理成使用文档、功能表或飞书文档时使用。典型触发包括：

- 整理成程序使用文档、飞书使用说明或 README；
- 整理项目功能、模块功能、软件能力或功能列表；
- 生成程序功能表、接口说明、部署说明或命令使用说明；
- 把一段已有程序说明改成适合飞书复制的文档。

以下请求通常不要使用本 Skill：只讨论代码、debug、修改程序、解释算法、通用 Markdown 排版，或不涉及程序内容的普通写作。

## 目标与边界

输出面向程序使用者和工程人员的 Markdown，做到结构清晰、技术信息准确、易扫描、可长期维护，复制到飞书后基本可以直接使用。

只能整理已有事实，来源可以是代码、README、用户描述、配置文件、命令、接口、日志、项目结构和已知功能。不得：

- 发明功能、参数、接口、使用步骤、性能指标或兼容性；
- 把推测、计划或部分实现写成“已完成”；
- 擅自改变技术结论、数字、版本号、路径、命令或状态；
- 为了填充模板生成空章节、空表格行或无依据的备注；
- 把设计文档、源码分析或算法推导当成默认交付物。

信息不足时，优先省略该项；必须保留但无法确认时写“待确认”。

## 与其他 Skill 的关系

本 Skill 是最终文档整理和输出层，不承担源码分析本身。若任务需要从陌生仓库、ROS、LeRobot、接口或部署环境提取事实，应先使用相应的代码分析或领域 Skill，确认入口、命令、参数、输入输出和状态后，再使用本 Skill 整理。

整理过程中遇到疑似代码问题，不修改代码；可以在文档中单独注明：

> 注意：该代码片段可能存在问题，建议进一步确认。

## 工作流程

### 1. 识别交付模式

根据用户目标选择一种主要输出模式，不要机械套用所有章节：

1. **程序使用文档**：用户需要了解程序用途、启动、操作、输入输出和故障处理时使用。
2. **功能表**：用户主要要求功能列表、功能表、模块能力或当前支持项时，优先使用表格。
3. **模块说明**：程序有多个模块，且用户要求解释模块职责、输入和输出时使用模块分节。
4. **接口/部署说明**：用户要求 Topic、Service、API、参数、安装、编译或部署时，补充对应的精确表格和命令。

可以组合模式，但应让最符合用户目标的内容占主体。

### 2. 提取事实

先按以下类别整理已确认信息：

- 程序名称、用途和解决的问题；
- 功能、模块、接口和当前状态；
- 操作系统、运行环境、依赖和硬件要求；
- 安装、编译、启动、停止、配置和使用步骤；
- 参数、默认值、输入、输出、文件、Topic、Service、API 和错误信息；
- 注意事项、限制、常见问题和更新记录。

对每项内容区分“已有证据”“用户明确说明”和“待确认”，只把前两类写成事实。项目结构只能证明存在文件或模块，不能单独证明功能已经可用。

### 3. 选择章节并输出

只输出实际有信息的章节。叙述性内容使用短段落和列表；字段、功能、接口和参数适合比较时使用表格；操作顺序使用编号列表；命令和代码使用 fenced code block。

默认不要添加开场白、客套话、总结性广告语或“如果需要我还可以……”等聊天内容，直接输出文档正文。

## 程序使用文档模式

按资料实际覆盖范围从下面选择章节，通常最多使用三级标题：

````markdown
# 程序名称

## 1. 功能简介

说明程序解决什么问题，以及主要用途。

## 2. 主要功能

| 功能 | 说明 | 使用方式 | 状态 | 备注 |
|---|---|---|---|---|

## 3. 运行环境

- 操作系统：
- 运行环境：
- 依赖：
- 硬件要求：

## 4. 安装 / 编译

```bash
原始命令
```

## 5. 启动方式

```bash
原始命令
```

## 6. 使用方法

1. 操作步骤。

## 7. 参数说明

| 参数 | 类型 | 默认值 | 说明 |
|---|---|---|---|

## 8. 输入与输出

### 输入

### 输出

## 9. 模块说明

## 10. 注意事项

## 11. 常见问题

### 问题 1

原因：

解决方法：

## 12. 更新记录
````

这是可选结构，不是必填清单。若某章节没有可靠内容，删除该章节。

## 功能表模式

用户主要要功能表、功能列表、模块功能或软件能力时，默认使用：

```markdown
| 功能模块 | 功能 | 说明 | 触发/使用方式 | 当前状态 | 备注 |
|---|---|---|---|---|---|
```

资料不足时可以简化为：

```markdown
| 功能 | 说明 | 备注 |
|---|---|---|
```

不要为了保持列数而编造“触发方式”“状态”或“备注”。“当前状态”必须来自明确资料；未知写“待确认”。

## 模块说明模式

每个模块优先说明作用、主要功能、输入和输出。例如：

```markdown
## 模块结构

### 1. 录制控制模块

**作用：**

负责控制一次数据录制任务的开始、结束和取消。

**主要功能：**

- 开始录制
- 停止录制
- 取消当前 Episode
- 管理录制状态

**输入：**

- 键盘命令
- ROS Service

**输出：**

- 录制状态
- Episode 数据
```

示例中的内容只用于展示结构；实际输出必须替换为当前程序已确认的内容，不能把示例功能当成事实。

## 命令、接口和代码保真

Shell 命令使用带语言标记的代码块；短命令可使用行内代码：

```bash
ros2 topic list
```

原样保留以下标识，不翻译、不改写、不规范化：

- 命令、参数和路径；
- Topic、Service、API、接口路径和配置项；
- 文件名、类名、函数名、环境变量和版本号；
- 代码逻辑、变量名、输出文本和错误信息。

允许增加代码前后的解释、标题和语言标记，但禁止修改代码、擅自修复代码或删除看似不重要的代码。如果代码片段有问题，只能按“注意”规则另行说明。

接口可按实际类型选择表格字段，例如：

```markdown
| 名称 | 类型 | 方向 | 参数/字段 | 说明 | 状态 |
|---|---|---|---|---|---|
```

缺少方向、类型或状态时删除该列或写“待确认”，不要猜测。

## 飞书友好格式

优先使用飞书可稳定渲染的标准 Markdown：

- `#`、`##`、`###` 标题，通常最多三级；
- `-` 无序列表和 `1.` 有序步骤；
- `**重点**`、Markdown 表格、fenced code block 和 `>` 注意事项；
- `- [ ]` 任务状态，仅在源内容确实表达待办时使用。

不要依赖 HTML、Obsidian 语法、MkDocs 扩展、Hugo shortcode 或自定义 Markdown 插件。表格用于稳定字段比较，不要把所有段落强行改成表格；长命令、路径和代码不要塞进表格。

## 状态与措辞

保持源资料的状态，不替用户做发布判断：

- 已实现、已验证、实验性、进行中、已废弃、未支持等状态只能在有证据时使用；
- 来源只说“计划”“准备”“可能”时，保留原状态或写“待确认”；
- 不把测试通过扩展为生产可用，不把文件存在扩展为功能完成；
- 不把默认配置扩展为用户本次任务实际勾选项，除非运行记录或生成配置明确证明。

## 交付前检查

输出前逐项检查：

- 是否真的在整理程序文档，而不是做通用 Markdown 排版；
- 功能、模块、参数、命令、接口、路径和数字是否都能追溯到已有资料；
- 是否把未知状态写成“待确认”，没有把推测写成已完成；
- 是否保留了命令、代码和技术标识的原样；
- 是否删除了没有内容的模板章节，避免过度使用表格；
- Topic、Service、API、参数和部署步骤是否适合工程人员直接执行；
- Markdown 是否只使用标准标题、列表、表格、引用和代码块；
- 最终输出是否可以直接复制到飞书，且没有聊天式前后缀。

使用此 Skill 时，至少用以下场景做一次针对性自检：README 转使用文档、程序描述转功能表、ROS 程序的 Topic/Service/参数说明、CLI 程序的命令说明、大量代码文档、信息不完整的说明，以及已经格式良好的 Markdown。重点检查不乱编功能、不改命令、不虚构状态、不生成空章节。
